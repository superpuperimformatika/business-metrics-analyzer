# Ответы на контрольные вопросы (ПЗ №2)

## 1. Чем отличаются бизнес-требования от функциональных и нефункциональных?
**Бизнес-требования** описывают, что организация хочет достичь с помощью программного решения: цели, показатели, ограничения (например, «сократить время формирования отчётов с 2–3 дней до 3 секунд»).
**Функциональные требования** описывают конкретные функции системы: что система должна делать (например, «система должна отображать дашборд с KPI»).
**Нефункциональные требования** описывают качество работы системы: производительность, безопасность, удобство, надёжность (например, «обновление KPI ≤ 3 секунд»).

## 2. Каким критериям должна соответствовать качественная User Story?
Критериям **INVEST**:
- **I**ndependent — независимая;
- **N**egotiable — обсуждаемая;
- **V**aluable — ценная;
- **E**stimable — оцениваемая;
- **S**mall — небольшая;
- **T**estable — проверяемая.

## 3. Зачем нужны критерии приёмки и как они связаны с тестированием?
Критерии приёмки (Acceptance Criteria) определяют условия, при которых User Story считается выполненной. Они напрямую связаны с тестированием: на основе критериев в формате Given-When-Then составляются тест-кейсы, которые проверяют соответствие реализации требованиям.

## 4. Какие элементы включает Use Case-диаграмма?
- **Акторы** — пользователи или внешние системы, взаимодействующие с системой.
- **Варианты использования (Use Cases)** — функции системы.
- **Связи** — ассоциации между акторами и Use Cases.
- **Границы системы** — прямоугольник, обозначающий границы приложения.

## 5. Что такое backlog и как он приоритизируется?
**Backlog** — упорядоченный список задач проекта, приоритизированный по бизнес-ценности. Методы приоритизации:
- **MoSCoW** (Must have, Should have, Could have, Won't have);
- **MoSCoW + Story Points**;
- **матрица ценность/сложность**.

## 6. Как связаны User Stories, Use Cases и backlog?
**User Stories** — краткие описания функций от лица пользователя. Они детализируются в **Use Cases** (сценарии взаимодействия). Все User Stories попадают в **backlog** с приоритетами и оценками, где упорядочиваются по бизнес-ценности для планирования спринтов.

## 7. Какие методы сбора требований вы знаете? В каких ситуациях они применяются?
- **Интервью** — для глубокого понимания потребностей заказчика.
- **Анкетирование** — для сбора данных от большой аудитории.
- **Наблюдение** — для выявления реальных процессов «как есть».
- **Анализ документов** — для изучения существующей документации.
- **Мозговой штурм** — для генерации идей и требований.
- **Прототипирование** — для уточнения требований через макеты.нужные строки.
